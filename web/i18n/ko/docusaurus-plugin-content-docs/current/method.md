# 방법

비교가 근거가 되려면 시험하는 변경이 유일한 차이여야 합니다. 양쪽의 기준 이미지,
도구, 프롬프트, 모델, 설정이 같아야 합니다. 양쪽에는 문제를 우회하는 방법까지 포함해
같은 도구를 보여 줍니다. 우회 방법을 빼면 차이가 부풀려집니다.

| 변경 | 라벨 | 무엇으로 증명하나 |
|---|---|---|
| 도구가 돌려주는 내용의 수정 | `before` = 부모 커밋, `after` = 수정 커밋 | 고정 호출 실행(scripted: 같은 호출, 모델 없음). 모델 실행은 에이전트에게 얼마나 중요한지를 보여 줍니다. |
| 모델이 읽는 내용의 수정 (도구 설명, 응답 필드, 오류 문구, 힌트) | 위와 같음 | 모델 실행만으로, 반복해서 (라벨마다 5번 이상. 온도 0에서도 결과가 달라집니다). |
| 기존 기능의 가치 | 한 커밋에서 `full`과 `without-<기능>` | 정답지 전체가 있는 조사 케이스에서 모델 실행. 그 기능이 일부 정답으로 가는 경로에 있어야 하고, 다른 경로는 열어 둡니다. |

모델 실행은 요약의 열을 비교합니다. 성공한 실행, 찾은 사실, 틀린 주장, 턴, 도구 오류,
끝난 이유입니다. 약한 쪽이 그래도 통과한 실행도 보고합니다. 그런 실행은 비용이 답이
아니라 턴과 시간에 드러난다는 것을 보여 줍니다. 범위도 밝힙니다. 더 돌리지 않았다면
데이터셋 하나, 모델 하나의 결과입니다.

이를 위해 케이스는 두 종류입니다. *수정 케이스*는 수정 하나가 바꾸는 것만 묻습니다
(`pcap-dns-smtp`, 검증 EXP-001에서 사용). *조사 케이스*는 공개
데이터셋의 정답지 전체를 묻고, 그 안의 모든 증거 종류에 맞는 도구를 줍니다
(`rhino-hunt`).

실행 방식(하네스)은 모델만큼 중요합니다. 9B 로컬 모델로 bench-runner는 수정 케이스는
잘 풀었지만(EXP-001), 검증으로 남기지 않은 탐색 실행에서 Rhino Hunt 답은 하나도 찾지
못했습니다. 반면 Claude로 돌린 `mulder investigate`는 4/7에 닿았습니다 (EXP-002,
scripted 상한 5/7). 조사 케이스에는 더 강한 모델이나 다른 실행 방식이 필요합니다. 무엇으로 돌리든 모든 라벨에서
같아야 합니다.

## 답 판정

모델의 답은 스크립트로 채점하지 않고 검토자가 판정합니다. 검토자는 답을 정답지와 비교해
질문마다 mulder 채점표와 같은 4단계(일치, 부분, 놓침, 오탐, [실행과 검토](running#검토) 참고)
중 하나로 판정합니다. 질문 밖에서 정답지나 증거와 모순되는 주장을 사실로 단정한 것도 기록합니다.
결과는 완전 일치, 탐지, 오탐을 질문 수에 대한 비율로, 검토한 실행들의 중앙값과 범위로 냅니다.
정답지가 공개돼 있어서 도구 호출 없이 맞힌 답은 찾은 것이 아니라 기억한 것일 수 있습니다.
그래서 검토 화면에 질문에 필요한 도구 중 무엇을 호출했는지 보여 줍니다.

scripted 실행(모델 없이 정해진 도구 호출)은 자동으로 확인합니다. 도구 출력에 질문의 기대
문자열이 모두 있으면(`expect.all`, `expect.any` 중 최소 `expect.min`개, 숫자만으로 된 값은 온전한
수로) 그 질문을 셉니다. 기대 문자열 하나가 사실 하나입니다. `./bench.sh check`는 이 수를 검증의
`scripted_expect`와 비교합니다.

`mulder investigate` 보고서는 검증이 요청한 경우 질문마다 `Case Q<n>:` 줄로 읽습니다
(`Case Q28-Q30:`처럼 범위로 쓴 줄은 범위 안의 모든 질문의 답).

## 고정 조건

모델을 뺀 모든 것이 Docker 안에서 돕니다. 증거 준비, MCP 서버, runner입니다. 릴리스
이미지는 digest로, 각 variant는 커밋 SHA로 고정하고, 실행마다 서버 커밋과 이미지 ID를
기록합니다. 모델은 호스트에서 돌고, 실행마다 모델 이름, 온도, 토큰 상한, 추론 설정을
기록합니다.
